How this works (the OKR SOP)

What this is

  • Keep one shared set of OKRs (Objectives and Key Results, plus Deliverables) for every role. Use it to stay teleological: every piece of work traces up to a priority agreed in advance
  • Keep the single source in COWORK/projects/OKRs/okrs.json. The page at https://vfhqi.github.io/landing/okrs/ is drawn from it; never edit the page by hand
  • Keep it simple: one file, one page, about five minutes a week. Expand only when Richard asks

The three levels

  • Objective (the quarter): the outcome for the quarter. Mark it Core (must achieve) or Aspirational (shoot for the moon). Give it a precise description sentence
  • Key Result (reach by a month, then hold): a state, never a one-off delivery. Make it specific and numeric, normally "Go from X to Y". Achieving all of an Objective's Key Results completes the Objective. Give each 2 to 4 per Objective
  • Deliverable (the week): a thing done that moves a Key Result. Give each Key Result 2 to 4 Agreed Deliverables live at once; Done ones are ticked and do not count
  • Make every Objective, Key Result and Deliverable pretty stretching: hard to achieve without creativity and very hard work
  • Link every Key Result and Deliverable to the item above it. When a Deliverable feeds several Key Results, list it under the most relevant one and show every link in the diagram
  • Present every level in stack-rank order, most important first

Names

  • Give every item a fixed short name of 1 to 4 words and never change it. Write it in single quotes followed by the level: 'Fully Invested Portfolio' Key Result
  • Never write "Key Result 1" or "Deliverable 3". Use the short name, every time, in every role

The One Thing

  • Name one Key Result each month as The One Thing. Show it at the top of the page and in the stand-up. Keep reminding Richard of it
  • October 2026: the 'Fully Invested Portfolio' Key Result

Proposed and Agreed

  • Let any role propose a Deliverable or a Key Result: in the stand-up, in a chat, or in the Friday list
  • Record every proposal as Proposed, with a one-line why, its value-add against its Key Result (High, Medium or Low), and a grade of how likely it is to be agreed: Probable, Plausible or Possible
  • Treat a Deliverable as Agreed only when Richard agrees it. Nothing else makes it Agreed
  • Mark it Done when finished, and keep it on the page, ticked

The weekly rhythm

  • Friday: the Chief of Staff sends Richard a stack-ranked list of 6 to 10 proposed Deliverables for next week, each with its why, value-add and Key Result, and last week's Agreed Deliverables marked done or not done. Give a range with reasons and a recommended order, never a single pick. Richard decides
  • Before Monday: record Richard's choices in okrs.json as the week's Agreed Deliverables and republish the page
  • Monday stand-up: show The One Thing and the week's Agreed Deliverables
  • High Performance Coach and Chief of Staff, every day: when work drifts from the OKRs, ask which Key Result it serves. If none, suggest parking it

The quarterly rhythm

  • Set the Objectives and Key Results before or at the start of the quarter
  • Let new Key Results emerge during the quarter, and refine wording lightly; record every change in projects/OKRs/decisions.md

Every role

  • Tag your work with the short name of the Key Result it serves. If it serves none, say so and ask Richard before doing it (in the chat, or through the Chief of Staff in the stand-up)

How to change it

  • Edit projects/OKRs/okrs.json; run python3 -B projects/OKRs/tools/build_okrs_page.py from the COWORK folder; publish with the landing page (LANDING_PUSH flag, see memory/skills/github-push/SKILL.md Step 0); record the change in projects/OKRs/decisions.md
